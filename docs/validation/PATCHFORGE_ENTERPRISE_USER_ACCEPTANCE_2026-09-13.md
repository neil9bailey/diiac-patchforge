# PatchForge enterprise candidate: user acceptance checklist

Prepared: 2026-09-13. Epic: `EPIC-PF-ENTERPRISE-READINESS-20260913`.

Status: **test plan, not a deployment or acceptance certificate**. Confirm the live release with the operator before starting; a familiar URL or a successful page load does not establish which build is running.

## Before you start

- Open [PatchForge](https://patchforge.diiac.io) after the operator confirms the candidate release. Record the URL, tested commit/image tag, date/time, browser/device, tester and assigned role. Keep passwords, access tokens and personal customer data out of screenshots and defect reports.
- Use an authorised customer/test scope and existing realistic records: a known asset/advisory, an analysed finding and, where available, two verified packs from different times. Agree any evidence submissions, reviews, source refreshes or new pack generation with that scope's owner. Do not invent evidence, seed production, alter access assignments, purge records or install a collector just to make these tests pass.
- Have a Reader account and an authorised working account available. Use actual Microsoft role assignments, not development preview roles. Evidence review also requires the role permitted for the particular evidence class; Admin alone does not prove all role journeys.
- Keep the original downloaded files unchanged. A document edited after download is no longer the exact artifact verified by PatchForge.

Use the visible navigation entries: **Patch & CVE Catalogue**, **Vulnerability Queue**, **Vendor Catalogue**, **Customer Estate**, **Ask PatchForge**, **Reports**, **Admin**, and **Getting started & guidance**. Open the navigation drawer first on a phone. "Guide" below means the page opened by **Getting started & guidance**; **Review & Approve** is reached through **Open evidence review**, not a separate main-navigation entry.

## UI tests and success criteria

Run the first nine tests for the main user journey. Tests 10-12 cover context, usability and safety. Start read-only; execute a write action only where the test scope already authorises it.

| # | What to do | Success criteria |
|---|---|---|
| 1. Sign in and role access | Use **Sign in with Microsoft**. Confirm your identity/tenant and open **Getting started & guidance**. Repeat with the Reader account. | The intended tenant and assigned roles are shown. Reader can inspect permitted data but cannot refresh sources, submit evidence or generate packs. A Security Lead, CAB Approver or Admin can generate packs; a CAB Approver is not thereby allowed to run triage analysis. Missing roles produce a clear restriction, not an apparent successful write. Record missing test accounts as blocked coverage. |
| 2. Find your next action | Open **Getting started & guidance**, read **Your next steps**, then follow **Browse patch and CVE catalogue**, **Set up customer estate**, **Open evidence review** and **Open decision packs and reports**. Return through **Getting started & guidance** between steps. | Each link reaches the intended area. Instructions explain who can act and what evidence is needed. Counts describe current tenant data, not an enterprise-readiness score. A failed load reads **Unavailable** and a loading request reads **Checking current tenant data**; unavailable data must not appear as a completed step or an authoritative zero. |
| 3. Source currency, not just connectivity | Open **Patch & CVE Catalogue** and inspect the catalogue currency text. If authorised, click **Refresh KEV** (accessible name **Refresh KEV intelligence**), then observe the result message. For an existing selected record, **Update selected EPSS** is the corresponding enrichment action. | The result message names the source and reports its outcome; failures remain visible. The catalogue stays usable and any refreshed records retain their source/review context. No new records can be a legitimate result and must not be presented as new intelligence. Catalogue generation time is not proof of the upstream feed's age. This visible action proves only the requested refresh; detailed feed-run timestamps/counts and unattended scheduling are operator checks below. |
| 4. Collector reporting versus trust | In **Customer Estate**, inspect an existing collector's **Lifecycle**, **Last seen**, **Last run**, **Last message**, **Version** and **Package digest**. | Current reporting is supported by a recent heartbeat/run, not registration alone. Stale/degraded/revoked states retain their reason and recovery guidance. A heartbeat or reported digest does not establish package-signature trust; that requires the operator's separate package check. No existing collector means this journey is blocked, not passed. |
| 5. Estate and applicability | Open the authorised asset in **Customer Estate**. Compare product, firmware, enabled/disabled features and management exposure with the customer's source evidence. Inspect **Exposure Matches**; where authorised, use **Patch Compare** with the intended asset, advisory and proposed version. | The result refers to the selected asset/advisory and distinguishes confirmed context from unreviewed statements or evidence gaps. A missing match is not interpreted as proof of safety. Explicit false/disabled values do not turn into positive exposure or exploitation claims. An applicability recommendation is not proof a patch has been installed. |
| 6. Finding and accountable evidence | In **Patch & CVE Catalogue**, search for and select the known finding; inspect **Selected decision context**, then click **Open evidence review**. Alternatively, use **Getting started & guidance** → **Open evidence review** and select the intended **Finding**. Check source references, affected scope and outstanding decisions. If authorised, submit a truthful evidence record and have the permitted reviewer use **Accept** or **Reject** with rationale. | Finding identity stays consistent. Evidence shows its class, revision/hash context, reviewer outcome and any expiry. Only the appropriate role can review that class. An outdated/conflicting review asks for refresh instead of silently overwriting a newer decision. Accepted evidence does not automatically close unrelated gaps or issue final approval. If no review is authorised, record the inspection separately and leave write-path coverage blocked. |
| 7. Prepare the selected pack | On **Review & Approve**, confirm **Finding** and **Governance posture**, then use **Generate Signed Pack** if authorised. Record the new pack ID and open **Reports**. | The generated pack belongs to the intended finding and tenant. Readiness, evidence gaps, verification and final approval are distinct. A signing/runtime failure is visible and does not produce a usable "verified" download. A pack with unresolved evidence can remain unapproved; that is not itself a generation defect. |
| 8. Exact pack and report QA | In **Reports**, use **Verified decision pack** to select the new pack, then an older verified pack. Compare **Selected pack**, **Finding context**, **Pre-Export Check**, **Report Content QA** and **Current Report Context**. | All report actions remain bound to the selected pack ID. Older packs retain their original context/currency. QA is shown only when bound to that exact pack; otherwise **No QA bound to selected pack** or the historical-context warning appears. A missing QA result is not converted into PASS, and signature verification is not described as content approval. Fewer than two suitable packs leaves historical-switch coverage blocked. |
| 9. Open the stakeholder outputs | For the selected verified pack, download DOCX and PDF for **Customer Patch Governance Pack**, **Board Vulnerability Summary**, **CAB Patch Decision Report** and **Technical Evidence Appendix**. Download that row's **Signed ZIP** and **Pack JSON**. Open every report and retain all original bytes for the operator. | Files open in the intended applications. Titles/audience, finding/pack identity, customer scope, evidence gaps, source references, approval state and available renderer metadata agree with the selection. Every page is readable: no clipped tables, overlapping text, blank required sections or raw errors. The ZIP opens and contains the expected pack material. Downloads for unverified packs remain disabled/rejected. A readable ZIP is not a cryptographic verification: exact-byte/member verification below must also pass before distribution as a signed artifact. |
| 10. Context switching | Only if two contexts are already authorised and available, switch while a previous view/request is still loading, then inspect Guide, finding selections and Reports. Do not save Admin configuration or enter an unapproved tenant to manufacture this test. | Old-context records, selections, messages and late results do not reappear under the new context. Access-denied/loading states do not display the previous tenant's data as current. Already-submitted server actions are not promised to be cancelled. If the deployment permits one tenant only, record this as blocked coverage; a UI-only test does not establish shared-MSP customer isolation. |
| 11. Keyboard and mobile | Without a mouse, use Tab/Shift+Tab/Enter through Guide, Reports, the pack selector, table controls and downloads. Repeat Guide-to-Reports at a narrow phone viewport or actual phone. | Focus is visible and follows usable order; controls work without a mouse or keyboard trap. The report table's scroll region can receive focus. Mobile navigation opens/closes, content remains readable and controls are reachable; the page has no unintended horizontal overflow. Any intentionally scrollable table remains usable. |
| 12. Safety and honest failures | Re-read **Understand the trust states**, **Human Decisions Required**, **Final approval** and, for a permitted Admin/Auditor, **System & Data Health**. Inspect any naturally occurring blocked/error outcome from these tests. | AI remains advisory. Generating a report, accepting one evidence record, a matching digest or an analysis completion cannot be mistaken for CAB approval, risk acceptance, installed patches or verified closure. Legacy digest inspection must not be called signature authenticity. Errors identify the failed action and retain a useful recovery path; never bypass verification or role checks to obtain a green result. |

## Operator checks: separate from user UI acceptance

These checks belong in the release evidence, not in a user's assertion that the screen looks correct. The operator records exact results; none is marked complete by this plan.

| Check | Required evidence / success criterion |
|---|---|
| Source and repository identity | Local released commit and intended remote branch resolve to the same source; preserved unrelated edits are disclosed. Record any source branch/worktree that is deliberately not merged. Release records identify the candidate actually built, not merely its earlier base commit. |
| Six-image Azure rollout | Capture the six expected app images/revisions and registry digests against the signed release manifest. Latest/ready revisions and traffic must match the intended release; report any mixed old/new set. A tag or health response alone is not source/digest proof. |
| Service and access health | UI, health/readiness and required internal services respond as expected; PostgreSQL, required authentication and required tenancy remain enabled. An unauthenticated protected API request is denied. Do not expose credentials in evidence. |
| Detailed source-run evidence | Read the protected source-feed run records for the tested tenant and refresh. Retain source/run ID, status, records seen/ingested/enriched, completion time and message. Failed/incomplete outcomes must not be mistaken for completed fresh intelligence. **Source Feeds / Recent Feed Runs** are not main-navigation entries in this build; do not require a user to find them to pass the visible catalogue-refresh journey. |
| Unattended scheduler | Verify the intended running-replica/scaling configuration and observe a scheduled cycle without using a manual UI refresh as its substitute. Record cycle/work IDs and times. All required work must complete before a success checkpoint; incomplete work retains incomplete status and no success checkpoint. Reconcile dead-letter/quarantined/exhausted work through the approved operator process. Source feed freshness and scheduler process availability are separate checks. |
| Exact artifact trust | For the freshly downloaded pack JSON, ZIP, DOCX and PDF, retain signing/manifest metadata and verify the exact delivered bytes. Verify every ZIP member against the signed manifest. Record the expected trusted key/version and results; matching hashes without authenticated signing provenance are insufficient. Any missing material, digest mismatch or signature failure blocks signed-artifact distribution. Follow the [operational user guide](../operations/PATCHFORGE_OPERATIONAL_USER_GUIDE.md). |
| Customer collector trust, if in scope | Verify the actual customer-distributed package/manifest and Authenticode trust separately from its heartbeat. Confirm an authorised real customer installation/import before claiming collector acceptance; a local development package is not evidence of that. Follow the [collector and automation runbook](../operations/PATCHFORGE_COLLECTOR_AND_AUTOMATION_RUNBOOK.md). |

## Record results and decide

For each test record: **Pass / Fail / Expected block / Blocked (not exercised)**, tester/role, timestamp, tenant and relevant asset/finding/pack/run IDs, observed result and evidence location. An expected permission/signature block can pass that safety control; it does not pass the missing happy-path journey. Do not label missing access, missing records or an untested feature as passed.

Defect template: **test number; build; role; safe reproduction steps; expected result; actual result; screenshot/error; relevant IDs; impact; owner**. Avoid secrets and unnecessary customer details. If data crosses contexts, approval is falsely asserted, an untrusted artifact is downloadable as verified, or report bytes/pack identity disagree, stop that journey and escalate immediately.

Acceptance requires all in-scope journeys exercised on the confirmed running candidate, no unresolved material defects, verified report artifacts and a named human reviewer recording the result. Capture agreed exclusions explicitly. A successful deployment and automated tests do not by themselves clear live UAT, security/compliance or the human release decision.
